Bienvenue sur l'API Wakyi

L'API Wakyi vous permet d'orchestrer des paiements Mobile Money B2C et C2B et de gérer vos wallets sur les opérateurs de Côte d'Ivoire. Elle est destinée aux intégrateurs B2B — e-commerce, fintechs, entreprises, institutions — et ne couvre que les endpoints publics destinés aux clients.

Orange Money MTN MoMo Wave Moov Money

Par où commencer

Générer une clé, faire un premier encaissement en 5 min.

Authentification

Headers X-API-Key + X-API-Secret, signature des webhooks.

Modèle de l'API

L'API est REST/JSON, versionnée sous /api/v1. Les opérations coûteuses (collecte, payout) sont asynchrones : l'API accuse réception (202), lance un traitement, puis vous notifie via webhook ou polling.

  • Méthodes mutantes : POST, PATCH, DELETE — toujours avec Idempotency-Key.
  • Lectures : GET. Trois listes seulement sont paginées (taille 50, maximum 200) ; voir Pagination & filtres.
  • Fuseau horaire : toutes les dates sont en UTC ISO-8601.
  • Devise : XOF uniquement. Les montants sont des entiers — le franc CFA n'a pas de subdivision. Un montant décimal est refusé en 400.
  • Numéros : format international sans +, 12 chiffres : 225 + numéro à 10 chiffres (ex. 2250701234567). L'opérateur est déduit du préfixe.
Périmètre de cette documentationSeuls les endpoints publics sont décrits ici. Les routes d'administration, les analytiques internes et les callbacks opérateurs ne sont volontairement pas exposés.
Démarrage

Démarrage rapide

Passer de zéro à un premier appel API réussi en 5 minutes : création de clé, encaissement de test, lecture du statut.

Récupérer vos identifiants. Connectez-vous à votre tableau de bord Wakyi et générez une paire de clés : X-API-Key (identifiant public, préfixé sk_live_ en production, sk_test_ en sandbox) et X-API-Secret, affiché une seule fois à la création. Stockez-le dans votre coffre de secrets.
Whitelister votre IP (production seulement). Pour les clés sk_live_, votre serveur doit être déclaré dans la liste blanche d'IP. Les clés sk_test_ n'ont pas cette contrainte.
Faire votre premier appel. Déclencher une collecte de 1 000 XOF vers un numéro Orange Money de test :
bashcurl -X POST https://api.wakyi.com/api/v1/send-mobile-money/c2b \
  -H "X-API-Key: sk_test_xxxxxxxxxxxxxxxxxxxxx" \
  -H "X-API-Secret: votre_secret_ici" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{
    "mobile_number": "2250700000001",
    "amount": 1000,
    "currency": "XOF",
    "transaction_reference": "TEST0001"
  }'
202 Accepted
json{
  "message": "Transaction acceptée, traitement en cours",
  "task_id": "a7f8e9c2-1234-4567-89ab-cdef01234567"
}
Récupérer le statut. Deux options : polling via GET /task-status/{task_id}/, ou (recommandé) webhook sur les événements transaction.completed / transaction.failed.
À lire avant d'écrire votre boucle de pollingUne réponse acceptée n'est pas un paiement abouti. /task-status/ vous dit où en est le traitement de votre requête ; l'issue réelle est le statut de la transaction (Completed, In Progress, Failed). Ne marquez rien comme payé avant Completed.

Environnements

Wakyi expose deux environnements totalement isolés : sandbox pour les tests, production pour le trafic réel.

EnvironnementDescription
SandboxBase URL https://api.wakyi.com/api/v1 — clés sk_test_*, livemode=false. Aucun appel opérateur réel, faux fonds, simulation de succès/échecs.
ProductionBase URL https://api.wakyi.com/api/v1 — clés sk_live_*, livemode=true. Soumise à la liste blanche d'IP. Tous les débits sont réels.

La base URL est identique ; c'est la clé (et son flag is_test) qui distingue les deux mondes. Vos données sandbox ne polluent jamais vos rapports de production.

Concepts

Authentification

Toutes les requêtes requièrent une paire clé/secret transmise en en-têtes HTTP. Aucune session ni token JWT n'est utilisé.

En-têtes requis

NomTypeDescription
X-API-KeyrequisstringIdentifiant de votre clé. Format : sk_live_* ou sk_test_*.
X-API-SecretrequisstringSecret associé. Renvoyé une seule fois à la création, jamais consultable ensuite.
Content-TyperequisstringToujours application/json, sauf pour le téléversement d'un lot (multipart/form-data).
Idempotency-KeyoptionnelstringObligatoire sur les endpoints de paiement et de transfert (voir Idempotence). Ignoré ailleurs. UUID v4 recommandé.
bashcurl https://api.wakyi.com/api/v1/wallet/ \
  -H "X-API-Key: sk_live_5f3a..." \
  -H "X-API-Secret: wK4n9..."

Réponses d'authentification

StatutDescription
401 UnauthorizedNon authentifié : clé ou secret manquant, invalide ou révoqué.
403 ForbiddenAuthentifié mais interdit : IP source non autorisée (production), service non activé pour le compte, ou clé sans droit de dépense tentant une écriture (code api_key_read_only).
429 Too Many RequestsQuota dépassé. Réessayez avec un backoff exponentiel.

Clés sans droit de dépense

Une clé peut être émise en lecture seule (read_only: true) : elle lit vos données et les exporte, mais ne peut ni les modifier ni engager de fonds. Toute écriture est refusée en 403 api_key_read_only. Son plafond de requêtes est distinct de celui de vos clés de paiement : le trafic d'un tableau de bord ou d'un prestataire ne consomme pas le quota qui sert à payer.

SécuritéNe commitez jamais le secret dans Git et ne l'exposez jamais côté frontend : c'est une clé serveur. Pour une rotation, générez la nouvelle clé, basculez votre intégration, vérifiez que tout le trafic l'utilise, puis révoquez l'ancienne.
Concepts

Liste blanche d'IP

En production, déclarer au moins une adresse IP est obligatoire : sans liste, une clé sk_live_ ne sert à rien. Cette protection ne s'applique pas à la sandbox.

Chaque clé sk_live_* est attachée à une liste d'adresses autorisées, IPv4 ou IPv6, déclarées une par une (pas de plage CIDR, comparaison en égalité stricte). L'IP retenue est celle du dernier maillon de X-Forwarded-For, c'est-à-dire le pair réellement connecté à notre proxy : si un NAT ou un proxy sortant se trouve devant vous, c'est son adresse que nous voyons.

Deux refus, deux gestes

  • Aucune adresse IP autorisée n'est déclarée pour ce compte — votre liste est vide : transmettez-nous vos adresses de sortie.
  • IP non autorisée pour cette clé API — votre liste existe, mais l'appel vient d'ailleurs : il faut y ajouter cette adresse.
Il n'y a pas d'auto-dépannageL'enregistrement n'est pas en libre-service : écrivez à infos@wakyi.com en citant le message de refus. Avant toute migration d'infrastructure (nouveau serveur, nouvelle région cloud, passerelle NAT), envoyez-nous la nouvelle adresse et attendez notre confirmation.
Concepts

Idempotence

Toute requête mutante doit porter un Idempotency-Key. C'est la garantie qu'un retry réseau ne provoquera jamais un double débit.

Vous générez une clé unique (UUID v4 recommandé) pour chaque opération logique. L'API mémorise la réponse pendant 24 h : tout appel ultérieur avec la même clé et le même payload renvoie la réponse en cache, sans rejouer l'opération. La clé est scopée à votre compte.

StatutDescription
200/202 (replay)Même clé + même payload : réponse en cache renvoyée, aucune nouvelle écriture.
409 ConflictMême clé, une requête précédente est toujours en cours de traitement.
422 UnprocessableMême clé réutilisée avec un payload différent : refus pour éviter l'ambiguïté.
400 Bad RequestEn-tête Idempotency-Key manquant sur un endpoint mutant.
bash# Première tentative
curl -X POST .../send-mobile-money/b2c -H "Idempotency-Key: 6fa4..." \
  -d '{"mobile_number":"2250700000001","amount":5000,"currency":"XOF"}'

# Réseau coupé ? Le client retente AVEC LA MÊME CLÉ :
curl -X POST .../send-mobile-money/b2c -H "Idempotency-Key: 6fa4..." \
  -d '{"mobile_number":"2250700000001","amount":5000,"currency":"XOF"}'
# -> renvoie la même réponse, n'envoie pas un deuxième payout

Générez la clé côté client au moment où l'utilisateur final déclenche l'opération, et persistez-la jusqu'à réception de la réponse finale.

Concepts

Approbation des paiements

Sur un compte qui délègue à des sous-utilisateurs, un paiement initié n'est pas envoyé : il attend la validation du titulaire. Sans délégation, rien ne change — vos appels partent immédiatement.

Un sous-utilisateur initie un payout. Les fonds sont immédiatement engagés (ils sortent du solde dépensable), mais rien ne part chez l'opérateur. Le titulaire approuve — l'envoi part alors — ou refuse, et les fonds sont rendus.

Ce que vous recevez à l'initiation

L'appel rend toujours 202. C'est la présence de la clé status qui distingue les deux cas, et c'est le seul point que votre code doit tester :

json// Parti chez l'opérateur — le cas habituel
{ "task_id": "8f3a...", "message": "Payout en cours" }

// EN ATTENTE de validation — aucun task_id
{ "status": "AWAITING_APPROVAL", "reference": "ORDER4821",
  "message": "Payment awaiting approval" }
Pas de task_id tant que ce n'est pas approuvéUn paiement en attente n'a pas de task_id : aucune tâche n'a été lancée. Testez la présence de status avant de lire task_id. Les endpoints de file, d'approbation et de refus sont décrits dans Paiements en attente.
Concepts

Modèle d'erreur

Les refus produits par le cadre applicatif — authentification, autorisation, quota, idempotence, validation — portent une enveloppe structurée. Les refus métier des endpoints de paiement portent une chaîne simple.

Le champ error est toujours présent, mais son type change. Si error est un objet, vous disposez d'un code machine. Si c'est une chaîne, seuls la phrase et le statut HTTP font foi.

json// Forme structurée — erreurs du cadre
{ "error": { "code": "permission_denied",
             "message": "Service 'Mobile Money' non autorisé pour ce compte.",
             "details": null } }

// Forme simple — refus métier des endpoints de paiement
{ "error": "Insufficient balance" }

Codes structurés

CodeDescription

not_authenticated (401)Aucun identifiant fourni sur une route protégée.
permission_denied (403)IP hors liste blanche, service non activé, ou ressource appartenant à un autre compte.
api_key_read_only (403)Clé sans droit de dépense tentant une écriture.
throttled (429)Plafond horaire dépassé. Le message indique le délai d'attente.
invalid (400)Validation de schéma (webhooks). details porte le détail champ par champ.
parse_error (400)Corps JSON malformé.

idempotency_key_required (400)En-tête Idempotency-Key absent sur un endpoint qui l'exige.

Refus métier des endpoints de paiement

StatutDescription
400 Bad RequestMontant absent, non entier ou négatif ; champ requis manquant ; numéro mal formé ; opérateur non reconnu ; devise autre que XOF ; solde insuffisant ("Insufficient balance") ; montant hors des bornes de l'opérateur ; transaction_reference trop longue ou au mauvais format.

Pagination & filtres

Trois endpoints de liste sont paginés par numéro de page : GET /transactions/, GET /webhooks/ et GET /webhooks/{id}/deliveries/. Les autres listes renvoient un tableau JSON nu.

NomTypeDescription

page_sizeoptionnelintegerDéfaut 50, maximum 200 (au-delà, ramené à 200 sans erreur).

  "next": "https://api.wakyi.com/api/v1/transactions/?page=3",
  "previous": "https://api.wakyi.com/api/v1/transactions/?page=1",
  "results": [ /* ... */ ]
}
Un paramètre inconnu ne provoque pas d'erreurTout paramètre non documenté est ignoré en silence et la liste complète est renvoyée en 200. Vérifiez l'orthographe : les bornes de date se nomment date_from et date_to.
Concepts

Wallets & transferts

Votre compte dispose de deux wallets XOF distincts. L'argent ne passe jamais de l'un à l'autre tout seul : il faut le transférer explicitement avant de pouvoir le dépenser depuis l'autre wallet.

WalletDescription
Mobile Money CollectionCrédité quand une collecte C2B aboutit — l'argent que vous avez encaissé auprès d'un payeur. Ne sert pas directement à financer un payout.
Mobile Money CreditDébité par chaque payout B2C. C'est le seul wallet dans lequel un payout peut puiser.
Le piège : « Insufficient balance » juste après une collecte réussieUne collecte C2B qui aboutit place les fonds dans Mobile Money Collection — pas dans Mobile Money Credit. Si vous tentez ensuite un payout B2C, l'API vérifie le solde de Credit, le trouve inchangé, et renvoie 400 "Insufficient balance". Les fonds existent ; ils sont sur l'autre wallet. Transférez-les d'abord avec POST /transfer-momo-collection-to-momo-credit/.

Le transfert est synchrone (la réponse donne le résultat immédiatement), sans conversion, au sein de votre propre compte uniquement, et exige un Idempotency-Key comme tout endpoint mutant.

Concepts

Sandbox

Un environnement totalement isolé pour tester votre intégration sans dépenser un franc et sans appel opérateur réel.

  • Clés préfixées sk_test_ (les sk_live_ ne fonctionnent pas en sandbox).
  • Aucun appel opérateur réel : un simulateur renvoie des réponses déterministes.
  • Wallets de test isolés, alimentés avec du faux argent (plafond 10 000 000 XOF par wallet).
  • Pas de liste blanche d'IP : n'importe quelle source est acceptée.
  • Tous les événements webhook portent livemode: false.

Pourquoi fournir votre propre référence

Un payout est asynchrone : la réponse 202 ne porte que le task_id, et le statut définitif arrive plus tard. transaction_reference est la clé qui relie cette issue à votre commande : la valeur que vous envoyez ressort sous le nom reference — dans le webhook comme dans GET /transactions/?reference= — et vous la détenez avant même que l'appel ne parte.

Les deux noms ne sont pas symétriquestransaction_reference (ce que vous envoyez) ressort sous reference. La réponse contient par ailleurs un champ nommé transaction_reference : c'est notre identifiant interne, pas le vôtre. Cherchez votre valeur avec ?reference=, jamais avec ?transaction_reference=. Une référence = une transaction ; tout le reste va dans metadata.
Référence API

Suivre un job asynchrone

Retourne l'état d'une tâche asynchrone. Approche polling — alternative aux webhooks, utile en développement.

GET/api/v1/task-status/{task_id}/
status est l'état de la tâche, pas l'issue du paiementstatus: "SUCCESS" signifie « la tâche s'est exécutée sans planter », pas « la transaction a abouti ». Un paiement refusé par l'opérateur rend aussi SUCCESS, avec la clé error dans result. Lisez result, pas status. Une transaction In Progress n'est pas livrée : attendez Completed via GET /transactions/?reference= ou le webhook.
StatutDescription
404Tâche pas encore démarrée (cas normal juste après le POST — réessayez), inconnue, ou résultat expiré (> 24 h).
200 — SUCCESSLa tâche s'est exécutée. Lire result : result.error présent = refusé ; result.success présent = accepté, pas encore nécessairement livré.
200 — FAILURELa tâche elle-même a échoué (panne de notre côté) ; error porte le détail.
json{
  "task_id": "a7f8e9c2-1234-4567-89ab-cdef01234567",
  "status": "SUCCESS",
  "result": { "success": "Payment request sent", "mobile_number": "2250700000001", "originatingID": "ORDER4821" },
  "error": null
}

Backoff conseillé : 2 s, puis 5 s, puis 10 s. Traitez les premiers 404 comme « pas encore prête » ; n'abandonnez qu'après environ 60 s sans transition.

Webhooks

Concept & signature

Recevez les changements de statut de vos transactions en push sur l'URL HTTPS de votre choix. Plus efficace que le polling, recommandé en production.

  1. Vous enregistrez une URL via POST /webhooks/.
  2. À chaque événement, Wakyi envoie un POST JSON sur cette URL, signé HMAC-SHA256 avec le secret de l'endpoint.
  3. Répondez 2xx pour accuser réception. Sinon, nous retentons selon l'échéancier ci-dessous.
  4. Les événements sandbox (livemode: false) et production (livemode: true) sont envoyés sur des endpoints séparés.

Vérifier la signature

La signature est HMAC-SHA256(timestamp + "." + corps_brut, secret). Vérifiez sur les octets bruts reçus, pas sur un JSON re-sérialisé ; validez que le timestamp est récent (< 5 min) pour rejeter les replays ; comparez en temps constant.

javascriptconst crypto = require('crypto');
// Express : app.use(express.json({ verify: (req, _res, buf) => { req.rawBody = buf; } }))
function verify(req, secret) {
  const header = req.headers['x-webhook-signature'] || '';
  const ts  = header.match(/t=([^,]+)/)?.[1];
  const sig = header.match(/v1=([0-9a-f]+)/)?.[1];
  if (!ts || !sig) return false;
  const expected = crypto.createHmac('sha256', secret)
    .update(ts + '.' + req.rawBody.toString('utf8')).digest('hex');
  return sig.length === expected.length &&
         crypto.timingSafeEqual(Buffer.from(sig), Buffer.from(expected));
}
